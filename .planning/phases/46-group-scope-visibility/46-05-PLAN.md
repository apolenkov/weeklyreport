# Phase 46-05 — `scope-denied` audit + cross-group integration tests

**Status:** ready
**Depends on:** 46-02, 46-03, 46-04 (helper applied at every callsite)
**Requirement:** UFB-040

## Goal

Lock the gate with end-to-end integration tests proving cross-group leaks are
blocked, and emit a structured audit event whenever a head/viewer tries to
read a specific row outside their scope (analogous to `role-denied`).

## Acceptance Criteria

- `apps/api/src/lib/audit-logger.ts` exports `scopeDenied({ userId, role, attemptedScope, resourceId })` and emits an `audit.scope-denied` event
- Every `findUnique({id})` in dashboard/archive/weeklyReport that returns a row outside the requester's scope emits the event before returning 404
- Integration test `apps/api/src/modules/group-scope.integration.test.ts`:
  - Seeds 2 groups (A, B), one head per group, one lead per group
  - Head of A queries dashboard for the only published report → sees only A sections
  - Head of A directly requests B-section by id → 404 + audit event captured
  - Viewer with access [A] queries archive → sees only A sections in every report
  - Viewer with access [] queries archive → sees zero sections everywhere
  - admin queries everything → sees both groups' sections
- `audit-events.test.ts` extended with the new event type
- 660+ api tests still green; new integration test counted on top

## Steps

1. Add `scopeDenied` to `audit-logger.ts` mirroring the shape of `roleDenied`
2. Wire emit calls into `getSubmissionDashboard`, `archiveService.detail`, `weeklyReportService.get` for the explicit-id read paths
3. Author the integration test with the matrix above; use existing test-utils for seeding
4. Extend `audit-events.test.ts` with one assert that a viewer probing a foreign report id produces exactly one `audit.scope-denied` envelope
5. Run full api suite + grep for new failures

## Verification Commands
