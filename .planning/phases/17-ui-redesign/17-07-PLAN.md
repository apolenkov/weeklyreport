# Phase 17 Plan 07 — Wave 6: Print/PDF + Integration Tests

## Objective

Build the print-optimized template for PDF export and write comprehensive
integration tests for all new API endpoints introduced in Wave 2.

## Requirements Closed

- **UI-20**: Print/PDF template consistent with web design

## Step 1 — Print/PDF Template (UI-20)

### File

`apps/web/src/app/(app)/reports/[reportId]/print/page.tsx`

### Layout

Print-optimized version of the Weekly Report:
- No navigation, no interactive elements
- White background for print
- Page breaks between sections
- Company header: department name, period dates, week label
- Portfolio Overview table
- Per-lead sections (same as Weekly Report but flat, no accordions)
- Escalations summary
- Footer: generated timestamp, page number

### CSS

```css
@media print {
  /* Hide nav, buttons */
  /* Force white background */
  /* Page break rules */
  /* Fit to A4 width */
}
```

### Playwright PDF generation

The existing PDF export flow (BullMQ job) navigates to `/reports/[id]/print`
and captures PDF. Verify:
1. PDF renders without JS-dependent content
2. Server-side rendered content is complete
3. Traffic light colors print correctly
4. Tables don't split across page breaks

## Step 3 — Integration Tests for Wave 2 APIs

### Test files to create

```
apps/api/src/modules/period/period.integration.test.ts

```

### Test scenarios per module

#### period.integration.test.ts (~12 tests)
- Publish: sets periodStatus to published, locks sections
- Publish: fails if already published
- Publish: records publishedAt + publishedById
- Reopen: sets periodStatus to reopened
- Reopen: fails if not published
- Reopen: records reopenedAt
- Authorization: non-head cannot publish
- Authorization: non-head cannot reopen
- Publish with pending submissions: still succeeds (warning only)
- Double publish: idempotent or error
- Reopen after reopen: returns to open state
- Published period: lead saveDraft fails

#### weekly-report.integration.test.ts (~8 tests)
- Active period: returns compiled report with all submitted sections
- Portfolio overview: worst-case aggregation correct
- Escalations: blocked stages and at-risk items listed
- Empty report: returns empty sections array
- Historical period: returns compiled data
- Submission count: matches actual submitted sections
- Lead sections: grouped correctly with items/risks/decisions/priorities
- Authorization: viewer can access (read-only)

#### fill-from.integration.test.ts (~6 tests)
- Fill from past period: copies items, risks, decisions, priorities
- Fill from: creates version snapshot before overwriting
- Fill from: own sections only (cannot copy other lead's data)
- Fill from: source section must be submitted
- Fill from: target section must be draft
- Fill from published period: works (source is read-only, target is current)

#### version-history.integration.test.ts (~8 tests)
- Autosave creates version snapshot
- Version list returns ordered snapshots
- Restore version: replaces current data
- Restore version: creates new snapshot of overwritten state
- Version pruning: keeps max 50 per section
- Version data: includes full form state as JSON
- Authorization: own sections only
- Restore on submitted section: fails

#### admin-settings.integration.test.ts (~5 tests)
- Get settings: returns defaults if not set
- Update settings: changes department name
- Update settings: toggles auto-create
- Update settings: changes deadline days
- Authorization: non-head cannot access

#### stage-assignment.integration.test.ts (~6 tests)
- Create assignment: valid user + stage + product
- Create duplicate: rejected (unique constraint)
- Delete assignment: removes successfully
- List assignments: returns all for a product
- Authorization: non-head cannot manage
- Invalid references: fails gracefully
