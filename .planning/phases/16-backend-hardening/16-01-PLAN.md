<objective>
Align Prisma ReminderRule schema with Zod contracts via a hand-edited migration, fix the Zod reportId nullability mismatch, and update all repository mapping functions to pass null instead of fake UUIDs.

Purpose: The init migration created ReminderRule with name/cronExpression/enabled columns, but schema.prisma now declares kind/fireAt/timezone/status/version. Running `prisma migrate dev` without hand-editing will drop old columns before converting data, causing data loss (Critical Pitfall v4-P3). The Zod schema requires reportId but Prisma has it as optional -- this causes Zod validation failures when a ReminderRule has no report.

Output: A safe migration SQL, aligned Zod schema, and clean repository mappings.
</objective>

Then hand-edit the generated migration SQL to include data conversion BEFORE dropping old columns. The final SQL must follow this exact sequence:

```sql
-- Step 1: Create new enums
CREATE TYPE "ReminderRuleKind" AS ENUM ('deadline', 'follow_up');
CREATE TYPE "ReminderRuleStatus" AS ENUM ('active', 'paused');

-- Step 2: Add new columns with defaults
ALTER TABLE "ReminderRule" ADD COLUMN "kind" "ReminderRuleKind" NOT NULL DEFAULT 'deadline';
ALTER TABLE "ReminderRule" ADD COLUMN "fireAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP;
ALTER TABLE "ReminderRule" ADD COLUMN "timezone" TEXT NOT NULL DEFAULT 'Europe/Moscow';
ALTER TABLE "ReminderRule" ADD COLUMN "status" "ReminderRuleStatus" NOT NULL DEFAULT 'active';
ALTER TABLE "ReminderRule" ADD COLUMN "version" INTEGER NOT NULL DEFAULT 1;

-- Step 3: Convert existing data (MUST come before DROP)
UPDATE "ReminderRule" SET
  "kind" = CASE WHEN "name" ILIKE '%follow%' THEN 'follow_up'::"ReminderRuleKind" ELSE 'deadline'::"ReminderRuleKind" END,
  "status" = CASE WHEN "enabled" = true THEN 'active'::"ReminderRuleStatus" ELSE 'paused'::"ReminderRuleStatus" END;

-- Step 4: Drop old columns
ALTER TABLE "ReminderRule" DROP COLUMN "name";
ALTER TABLE "ReminderRule" DROP COLUMN "cronExpression";
ALTER TABLE "ReminderRule" DROP COLUMN "enabled";

-- Step 5: Remove default from fireAt (only needed during migration)
ALTER TABLE "ReminderRule" ALTER COLUMN "fireAt" DROP DEFAULT;
```

If Prisma generates additional changes (e.g., index modifications), keep them but ensure the UPDATE statements appear before any DROP COLUMN statements.

After editing, apply the migration: `pnpm exec prisma migrate dev`

Verify seed data survives by running: `pnpm exec prisma db seed` (per D-16). The seed.ts does NOT create ReminderRule rows, so it should run cleanly without touching the migrated table.
