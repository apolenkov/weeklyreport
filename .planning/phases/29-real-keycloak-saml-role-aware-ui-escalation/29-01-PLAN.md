<objective>
AUTH-08 closes the audit gap that has been open since the v5.0 milestone: there is no machine-readable record of who logged in, who was denied a role-gated route, and who logged out. Today, login success / failure are visible only as ad-hoc info() / warn() lines whose key names drift between callsites. This plan introduces a thin wrapper, `createAuditLogger`, that forces every role-effecting event through one envelope: `{event, userId, role, attemptedRole?, ip}`. The wrapper composes onto the existing AppLogger (Phase 26 nestjs-cls correlation IDs) — there is no new transport, no new file rotation, no new env var.

This is plan 29-01 because it has zero dependencies on the other Phase 29 plans (per CC-1 sequencing): no SAML changes, no UI changes, no new BullMQ queues. It can land first and the audit signal will already be capturing today's `protectedProcedure` denies (Phase 27 / Plan 04 default-deny gate) — providing baseline log-volume data that Phase 29 / 04 (SAML cut-over) will shift. Per A-1 (PITFALLS.md §1), defense-in-depth means the audit emit must live in the requireRole middleware itself, NOT only at controller seams — so when SAML middleware in Plan 29-04 adds new deny conditions, the same audit event continues to fire without code changes.

Per CC-2 (PITFALLS.md), DEV_SESSION removal is staged across Plans 29-02..04 and is NOT touched here. The audit logger must work whether the session originates from real SAML or from `AUTH_DEV_MODE_ALLOW_TEST=true` — it reads from `ctx.session` only, which is the seam shared by both paths.

Out of scope for this plan: any change to JWT shape (29-02), SSR layout gates (29-03), Keycloak cut-over (29-04), escalation digests (29-05), or navigation hides (29-06).
</objective>

  <files>apps/api/src/lib/audit-logger.ts, apps/api/src/lib/audit-logger.test.ts</files>
  <action>
    Step 1.1 — Create `apps/api/src/lib/audit-logger.ts`. The module imports `AppLogger` from `./logger.js` and exports:

    ```typescript
    import type { AppLogger } from './logger.js';
    import type { Role } from '@customreport/shared';

    export type AuditEvent =
      | 'login-success'
      | 'login-fail'
      | 'logout'
      | 'role-denied';

    export type AuditEnvelope = {
      readonly event: AuditEvent;
      readonly userId: string;
      readonly role: Role | 'unknown';
      readonly attemptedRole?: ReadonlyArray<Role> | Role;
      readonly ip: string;
    };

    export interface AuditLogger {
      loginSuccess(input: Omit<AuditEnvelope, 'event' | 'attemptedRole'>): void;
      loginFail(input: Omit<AuditEnvelope, 'event' | 'attemptedRole'> & { reason: string }): void;
      logout(input: Omit<AuditEnvelope, 'event' | 'attemptedRole'>): void;
      roleDenied(input: Omit<AuditEnvelope, 'event'>): void;
    }

    export function createAuditLogger(logger: AppLogger): AuditLogger {
      return {
        loginSuccess: (input) =>
          logger.info('audit', { event: 'login-success', ...input }),
        loginFail: (input) =>
          logger.warn('audit', { event: 'login-fail', ...input }),
        logout: (input) =>
          logger.info('audit', { event: 'logout', ...input }),
        roleDenied: (input) =>
          logger.warn('audit', { event: 'role-denied', ...input }),
      };
    }
    ```

    Note the strict-mode shape — every field is `readonly`, `attemptedRole` is optional only on `roleDenied`, and `loginFail` carries an extra `reason` string for the SAML / token-verify failure path.
