<objective>
Phase 28 / Plan 28-03 closed NOTIF-01/03/04 (T-24h deadline reminders) but explicitly deferred NOTIF-02 (T+2h escalation), NOTIF-05 (per-user opt-out), NOTIF-06 (BullMQ rate-limit + DLQ badge). This plan closes all three together because they share one schema migration (`User.notificationOptOut`), one queue (`email-reminder`), and one scheduler — splitting them would inflate the diff with no testability gain.

The escalation digest is the reverse-shape of the deadline reminder: the deadline reminder fires per-lead T-24h, the escalation fires per-head T+2h aggregating ALL late leads. The dedupe key shape is identical (`${rule.id}:${kind}:${cycleDate}:${recipientEmail}`) and the BullMQ pipeline is reused — no new queue, no new worker, just additive code paths in the existing scheduler/service/processor trio.

Per CONTEXT.md success criteria: NOTIF-02 escalation is NOT opt-outable (heads must always be notified of misses), NOTIF-05 deadline reminders ARE opt-outable. The opt-out branch lives in `RemindersService.requestReminderExecution` and is consulted ONLY when `kind==='deadline'` — escalation skips the flag check entirely.

Per A-1 (PITFALLS): the admin DLQ badge is a UX-only signal and does NOT replace any role gate — `admin.dlqCount` uses `headProcedure` (admin/head only) so a viewer cannot enumerate the DLQ even via tRPC. The badge is the same trust-boundary discipline the rest of the admin shell follows.

depends_on=[29-04]: this plan should land after the SAML cut-over because it adds new tRPC procedures (admin.dlqCount) that consumers will reach for via the real-SAML flow. Earlier ordering would couple the migration with the auth cut-over, broadening the rollback surface.

Out of scope: navigation hides (29-06 — last per CC-1).
</objective>
