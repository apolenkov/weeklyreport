# D6 — Archive Snapshots: что сохраняется при архивации периода?

**Дата:** 2026-05-14  
**Источник:** UAT-вопрос «когда период архивируется — останутся слепки?»

## Текущее состояние

Модель `Report` в `prisma/schema.prisma` не имеет отдельной snapshot-таблицы.
Архивация = флаг `archived = true` + переход `periodState → archived`.
Все данные остаются в тех же таблицах: `Report`, `ReportSection`, дочерние записи
(`WorkItem`, `Risk`, `Decision`, `Priority`, `Traffic`).
Связи сохранены через `reportId` / `reportSectionId` — каскадный `onDelete` не
срабатывает при архивации, только при явном удалении.

## Что может пойти не так

- Если `ReportingGroup` или `Project` удалят из системы — их `name` / `code`
  в дочерних записях не денормализован. Исторический отчёт потеряет название
  группы/продукта.
- `weekLabel` у `Report` уже денормализован (сохраняется как строка) — это
  правильный паттерн.

## Рекомендация

**Оставить текущий подход** (нет отдельной snapshot-таблицы), но добавить
денормализацию названий при архивации:

- Перед `periodState → archived` скопировать `group.name → Report.groupNameSnapshot`,
  `project.name → ReportSection.productNameSnapshot` (nullable поля, backfill = null).

Альтернатива — полный JSON-снимок (отдельная таблица `ArchiveSnapshot`) — избыточна:
данные уже хранятся через FK, отчёты читаются через JOIN'ы, дублирование удвоит
объём хранилища без выигрыша в скорости чтения.

## Компромисс

```
Минимальный патч (денормализация строк)
  + Исторические названия не ломаются при удалении группы/продукта
  + Нет миграции объёма данных
  - Нужна миграция схемы (2 nullable колонки) + заполнение при архивации

Полный снимок (JSON blob)
  + Полная изоляция от любых будущих схемных изменений
  - Удваивает хранилище, сложнее индексировать, труднее поддерживать
```

**Решение руководителя:** принять минимальный патч или оставить как есть
(риск — при удалении группы/продукта история сломается).
