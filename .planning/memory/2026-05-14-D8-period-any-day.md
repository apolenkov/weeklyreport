# D8 — PeriodsSubTab: свободный выбор дня начала периода

**Дата:** 2026-05-14  
**Источник:** UAT «при выборе периода я могу любой день в периоде выбрать»

## Текущее состояние

Периоды создаются с фиксированными границами: `periodStart` (понедельник) и
`periodEnd` (воскресенье). Длина задаётся `AppSettings.periodLengthDays`.
В UI выбор производится по `reportId` (path-segment `/lead/report/<id>`);
пользователь выбирает период из списка готовых записей, а не произвольные даты.

## Интерпретация UAT-вопроса

Вероятно, пользователь имеет в виду: «могу ли я кликнуть на дату внутри периода
и попасть на нужный отчёт», а не «могу ли я создать отчёт с произвольными
границами». Это навигационная UX-задача, а не изменение модели данных.

## Рекомендация

**Оставить фиксированные недельные границы**, но улучшить навигацию:
добавить в `PeriodNavigator` вспомогательную подсказку «любая дата этой недели
ведёт на один отчёт» — или date-picker, который при выборе даты маппит её
на ближайший `reportId` (fuzzy-поиск по `periodStart ≤ date ≤ periodEnd`).

Альтернатива — свободные границы дат — сломает шаблон PDF-отчёта
(он рассчитан на 5-рабочих-дней формат), усложнит логику дедлайнов
и auto-archiver-расчёт.

## Компромисс

```
Date-picker → маппинг на существующий reportId
  + Нет изменений в схеме и бизнес-логике
  + Интуитивно: клик на любой день недели → тот же отчёт
  - Нужен небольшой UI-компонент (date-picker + query по диапазону)

Свободные границы периода
  + Максимальная гибкость
  - Ломает PDF-шаблон, дедлайн-логику, auto-archiver; риск: периоды
    начнут пересекаться (PARTIAL UNIQUE INDEX не защитит произвольные диапазоны)
```

**Решение руководителя:** уточнить, нужен ли date-picker (навигация) или
реально нужны произвольные границы периода.
