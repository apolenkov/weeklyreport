# Lead form regression coverage

The suite is node:test driving the pinned agent-browser CLI 0.39.0 (verified at
start-up by `e2e/setup/agent-browser-version.ts`). Run it with `pnpm test:e2e`
against the running web/API; it resets and seeds `customreport_e2e` with Redis
DB 15 before every test, so exactly one e2e process may use that database at a
time: a second process (another session, an agent, an IDE run) wipes it
mid-test and shows up as `P2025` seeder failures or fields that lose their
value. The e2e global setup accepts `customreport_e2e` by default; setting
`E2E_LANE=a` or `b` selects the provisioned lane database
(`customreport_e2e_lane_a_test` with Redis DB 1, `customreport_e2e_lane_b_test`
with DB 2) instead, and the setup then accepts only that lane's database and
Redis DB, from both the environment and the running app. Two runners with
different lanes share no data, but each lane still allows one process at a
time and must be claimed first (coordinator-inbox `LANE`), because API
integration tests and manual checks use the same lane databases. A lane run
needs its own app: API `PORT` and `API_URL`, web `--port`, `DATABASE_URL`,
`E2E_DATABASE_URL`, `REDIS_DB` for that lane, and `E2E_BASE_URL` pointing at
that web origin. The denominator is the controls a Lead can reach
through `/lead/report` and `/lead/report/<reportId>`, including Report, Slides
and their dialogs. Head actions appear only where they complete a Lead
lifecycle scenario.

The inventory has **72 rows: 63 mapped capability groups and 9 explicit
source-only/execution dispositions**, reconciled against the actual actions,
assertions and source rather than titles alone. The suite authors **124
browser cases**. Conditional subcases without a written test are **NOT VERIFIED
(test not written/no valid fixture)** below; an absent or unreachable product
control is **N/A** with its source rationale.

The browser-free safety/helper tests in `e2e/setup/*.test.ts` are a separate
denominator run by `pnpm test:e2e-setup` (part of `pnpm test`); they do not
prove a Lead browser flow. Authored tests, unit tests and static gates are not
browser runtime evidence; run results belong to the run log outside the
repository. Same-SHA remote CI is verified separately.

Assistant response tests use a declared deterministic tRPC-response stub; they
prove UI response handling only, not backend answer generation or a live
model/provider response.

Wait policy: only CLI `open` has a 180-second outer process bound (cold
browser start, page load and the CLI's socket attempts; `open` has no
`--wait-until` option). Other commands and close retain 40 seconds, cleanup
45 seconds, and observable AX/URL waits 25 seconds. The wrapper adds no sleeps
or retries.

`button: Name` identifies the accessibility role and exact accessible name,
unless marked as a pattern. The node:test harness drives agent-browser CLI role
locators and freshly observed accessibility-tree refs. Scope repeated names to the named unit `article`,
week `group`, form or dialog. Chrome AX exposes the headings `Products` /
`Project activities` and week prefixes `PREVIOUSLY PLANNED`, `CURRENT WEEK` and
`NEXT WEEK`; week groups include the date/period because ColumnHeading labels
both lines. Scope by those observed prefixes, not exact bare or title-case week
names. Forms/radios retain their actual title-case accessible labels. Report
and Slides links are scoped to View mode because Main navigation also has a
Report link. `<item>` is a short test-owned description:
`apps/web/src/shared/lib/format/short-label.ts` flattens whitespace and truncates
action names to 60 characters with `…`. Native `<summary>` controls without an
explicit ARIA role appear as native `DisclosureTriangle` nodes in the observed
Chromium AX snapshot; that tree name is not an ARIA role. Table notation
`summary: Name` identifies the real disclosure and its accessible name. Some
summaries have no ref: assert the strict named scope count and use the CLI's
supported native `find role DisclosureTriangle ... --name ... --exact` command.
Use fresh snapshot refs for referenced controls; do not invent a button alias. Named
structural groups/forms/dialogs can have no ref; scope by their accessibility
subtree rather than requiring a ref on every container. More actions and
History are disclosures, not menus with menuitem roles.
Item, Risk, Decision and reopen editors use `dialog`; delete, discard, submit
and fill confirmations use `alertdialog`. Risk and Decision cards are plain
`div` elements, not `article` roles; choose their named action buttons or unique
Slides disclosure records instead of inventing semantic containers.
The native decision date input has no implicit ARIA role. Its `Deadline` label identifies the native field; interactions use fresh `spinbutton` refs from the scoped dialog and stable `aria-valuemin`/`aria-valuemax` ranges, without inventing locale-specific segment names. The test presses digits or Backspace, blurs through the named Impact field and reads the label-associated ISO value to assert save/clear before Save and after reload. Read-only DOM assertions do not mutate the field. Await observable conditions and save acknowledgements, never timeout sleeps.

A click that edits the draft turns the save control dirty only after the next
render, so a test that saves right after such a click uses `saveChanges` (a
bounded wait for the dirty state) instead of `saveDraft`, otherwise the helper
sees a clean draft, clicks nothing and the reload drops the edit.

Shared `waitScope`, `waitClosed` and `waitButton` use bounded observed AX
snapshot polling because the CLI has no role-wait command; no fixed sleeps are
used. For ordinary scopes, `waitScope` returns the matching snapshot. Dialogs
add a read-only wait for the actual role/name, no running surface animation and
a center hit target inside that dialog, then return a fresh observed snapshot.
`scopedRef` uses this existing readiness wait before reading its named target;
dialog assertions wait explicitly before direct snapshot reads. Shared waits
do not require `aria-modal`: the Report chat Sheet does not expose that
attribute. Section-editor `waitModal` preserves its own modal precondition
locally. Strict read-only opener-focus assertions live in
`e2e/lead-form/focus.ts`, shared without new lint exemptions or scripted focus
restoration. Auth/report-entry helpers live in `e2e/lead-form/access.ts` and
reuse the same 25-second `waitSnapshot`/`waitScope` policy: verify the native
dev-login role/email, observe the `getUrl` pathname and wait for the named report
surface. `waitNotification(text, session)` reuses the same 25-second snapshot
wait for exact StaticText inside `Notifications alt+T`. Pending Fill and reopen
use it; three pending Slides saves observe their success notification before
the retained modal-close checks. Navigation waits for `+ Add risk`; concurrent
conflict recovery waits for its exact recovery-region text and error notification.
All persistence, request-count and dialog assertions remain. These ten
offline-return cases use AX waits; native text waits remain elsewhere.
These waits do not force or retry clicks. Expandable support sections await their real `aria-controls`
panel's platform animation completion before clicking moving controls. Full
tRPC `{ json, meta }` inputs are decoded with the existing `superjson` serializer
before canonical save-schema checks; no browser adapter is added.

## Independent fixture and verification contract

- Each test owns its report/section state. Mutating tests must not depend on a
  preceding test, worker order or owner data. Global setup validates runtime
  configuration and initializes the owned session base without a reset. The
  automatic per-test fixture performs guarded reset/seed; node:test uses serial
  execution to isolate the shared authorized database. Explicit minimal
  conditions prepare that profile in their own test.
- Required fixture categories: current open/reopened draft; owning Lead and
  Head; another co-owner with private notes; Products with one/multiple owned
  stages; linked and standalone Activities; current and explicit Next records
  with stable lineage; Previous immutable snapshot; older published/archive
  items in paused/postponed/in-progress/planned/completed/cancelled states;
  automatically paused Current plan; carried continuation and explicit-Next
  precedence; long text and more than two lineage rows; covering risk; submitted
  fill sources, archived picker options, no-source and empty/unassigned cases. The no-source case explicitly uses the canonical `minimal` seed profile (`prisma/seeds/minimal/seed-minimal.ts`) after its own guarded preparation; the ordinary cases use `demo` plus the declared E2E overlay.
- The O18 item-count condition explicitly calls
  `prepareE2eData("demo", signal, "section-item-limit")` after its ordinary
  per-test baseline, just as minimal conditions prepare their own specialized
  state. The demo-only variant reuses canonical seed and normal overlay, passes
  the destructive guard, asserts expected owner/baseline count before mutation
  and fills exactly 100 valid own items with a final count assertion. Both
  parent and child reject another profile before reset. All fixture writes stay
  in the owned cancellable preparation group; the browser test creates no
  database client. Ordinary demo/minimal cases and the single automatic
  `beforeEach` reset are unchanged.
- History fixtures must include immutable published snapshots where the read
  model requires them. A persisted draft row alone does not prove Previous or
  Open work is rendered. Outcome, restore and week-move assertions compare
  observable historical text/lineage before and after the action.
- Guarded setup accepts **only `customreport_e2e`**, validates loopback through
  `prisma/guards/_destructive-guard.ts`, requires
  `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION='давай'` on each destructive
