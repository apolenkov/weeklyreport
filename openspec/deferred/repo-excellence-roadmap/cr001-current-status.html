Итог сейчас: свежий runtime дошёл до webServer, но остановился до browser survey. Предыдущий запуск на SHA 11c98223 дошёл до terminal capacity failure в continuation canary, но Sol указал, что failure-frontier callback был подключён не к тому режиму. На текущем SHA cac4e90a этот seam удалён, source manifest и Sol gate прошли. Единственный свежий monolithic capacity survey завершился тайм-аутом webServer: Next/Turbopack не разрешил внутренний font-модуль. Результат survey не опубликован; полный CR-001 не закрыт.

Правильный порядок

  1. Пересоздать source manifest для cac4e90a и получить Sol PASS.
    Выполнено. После любого изменения старые runtime-материалы считаются историческими; для следующего запуска потребуется новый exact-SHA review.
  2. Устранить webServer startup blocker и получить новый Sol gate.
    Только после этого повторно привязать 5.14, 5.15 и 5.17; повтор и изменение лимитов без решения Sol запрещены.
  3. Восстановить pending branch и доказать 5.19.
    Сначала offline извлечь четыре шага из trace и проверить все predicates; только затем выбирать диагностический atom или source-bound repair. Не увеличивать лимит и не вырезать ветви.
  4. Снять полный desktop-пакет и провести визуальное ревью.
    Скриншот сам по себе не является ревью.
  5. Закрыть данные, Redis, безопасность, выпуск и финальный Sol.

Как экономим ресурсы

  • Один координатор и один автор изменений для пересекающихся файлов.
  • Luna и детерминированные команды — для рутинного сбора и проверок.
  • Sol — только для архитектуры, спорных решений и контрольных вердиктов.
  • OpenCode — только для узкой, безопасной, читаемой задачи без секретов и runtime-данных.
  • Браузер, база и Redis не запускаются параллельно без разных подтверждённых ресурсов.
