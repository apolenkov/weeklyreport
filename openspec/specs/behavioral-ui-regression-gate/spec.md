# behavioral-ui-regression-gate Specification

## Purpose

Define a durable, code-derived Scenario Catalog that a swappable human or AI Driver executes with per-role accessibility verdicts before critical paths become a frozen gate.

## Requirements

### Requirement: Durable behavior-anchored Scenario Catalog

UI behavior SHALL be defined in a durable, high-level **Scenario Catalog** of
Behavioral Scenarios (`role + route + intent + Given/When/Then` expected
outcome), anchored to observable behavior, never to a code location
(`file:line`). The catalog SHALL be stored as a YAML skeleton (`role · route ·
intent`) with the expected outcome as Given/When/Then prose, read and edited by
both humans and the Driver. It SHALL NOT exhaustively enumerate every element,
state, or transition.

#### Scenario: Scenario anchored to behavior, not code

- **WHEN** a Behavioral Scenario is authored for a role/route
- **THEN** it describes only observable behavior (visible DOM, role/aria, console
  state) and contains no `file:line` reference, so it survives a refactor that
  moves the implementing code

#### Scenario: Catalog stays high-level, not exhaustive

- **WHEN** the catalog is reviewed
- **THEN** each entry is a `role × route × intent` scenario, and the catalog does
  NOT contain a frozen per-element/per-transition enumeration — that coverage is
  produced by the Driver at run time

### Requirement: Catalog generated from code, human-reviewed

The catalog SHALL be generated by a Haiku fan-out over the **code** entry-point
surface — the role's reachable routes (resolved from the SSR layout guards) plus
each route's page/action components — one agent per route (each navigating large
files to their action surface — the tRPC mutation call-sites and action
components — rather than reading linearly), followed by a completeness-critic
pass and a coverage matrix,
then reviewed by a human. It MUST NOT be hand-authored scenario-by-scenario, and
MUST NOT bind any scenario to `file:line`. The generator reads CODE only; the DOM
is the Driver's run-time concern, never the generator's.

#### Scenario: Generation derives scenarios from entry points

- **WHEN** the generator runs
- **THEN** it discovers the role-reachable route surface itself (from the SSR
  guards, no hardcoded routes or line numbers) and emits one set of Behavioral
  Scenarios per route, reading code without driving the live DOM

#### Scenario: Entry-point coverage is justified, then repaired

- **WHEN** generation completes
- **THEN** a completeness-critic pass and a coverage matrix verify **entry-point
  coverage** — that every `role × route` entry point has at least one intent
  scenario — and any flagged route (no intent, a vacuous `then`, or a structural
  leak) is re-extracted in a bounded repair loop; only items still unresolved
  after the bound are left for human review. This is coverage of entry points,
  NOT a per-element/per-transition enumeration; the latter is produced by the
  Driver at run time (see the per-role sweep)

#### Scenario: Intent ids stay stable across regenerations

- **WHEN** the catalog for a role is regenerated and a prior `<role>.yaml` exists
- **THEN** the generator reuses the existing `id` for an intent that is the same
  in meaning and mints a new `id` only for genuinely new behavior, so historical
  sweep reports keyed on `id` stay comparable

### Requirement: Swappable Driver (human or AI agent)

The Scenario Catalog SHALL be executable by a swappable **Driver**: either a
human (manual checklist) or an AI agent driving the browser via the Playwright
MCP through `/auth/dev-login`. Both read the same catalog. The agent Driver SHALL
be built on the repo's own tooling (Workflow + Playwright MCP), not an external
agentic-testing product.

#### Scenario: The same catalog runs under either driver

- **WHEN** a role's scenarios are executed
- **THEN** a human Driver can walk them as a checklist and an AI-agent Driver can
  drive them in a live browser, both from the same catalog, with no per-driver
  fork of the scenarios

#### Scenario: Agent driver uses owned tooling

- **WHEN** the AI-agent Driver runs
- **THEN** it drives the browser via the Playwright MCP and logs in via
  `dev-auth`, with no dependency on an external testing service

### Requirement: Deterministic frozen gate remains deferred

Freezing every behavioral scenario into deterministic Playwright specs as a
blocking gate SHALL remain deferred until the product stabilizes. The
entry-point UAT sweep MAY block on console, load, network, page, and axe
anomalies without becoming an exhaustive frozen behavior suite. Future frozen
scenarios SHALL cover only critical, stabilized paths.

#### Scenario: Accessibility blocking does not freeze the full catalog

- **WHEN** the entry-point sweep blocks on an axe violation
- **THEN** no exhaustive per-element expected-outcome specification is added
- **AND** formal scenario freezing remains deferred until the product stabilizes

#### Scenario: No exhaustive compiled gate is added now

- **WHEN** this closeout adds a blocking verdict to the existing entry-point
  UAT sweep
- **THEN** it does not add an exhaustive compiled per-element behavior gate
- **AND** the frozen critical-journey gate remains deferred until those paths are
  stable

### Requirement: Test-harness boundary

The owned UI e2e sweep harness SHALL remain under `e2e/sweep/` (Playwright
config, catalog sweep, fixtures, `dev-auth`, page helpers, visual helpers, and
the `test:uat` script). It MUST keep the integration suite
(`e2e/integration/*`, `playwright.integration.config.ts`) and all Vitest unit
tests. The sweep's `dev-auth` plumbing is a live source owner and MUST stay
available to the per-role driver.

#### Scenario: Integration and unit tests are preserved

- **WHEN** the UI e2e sweep runs
- **THEN** `pnpm test` (Vitest unit), `pnpm test:uat` (the sweep), and the
  integration config remain runnable, and no unit or integration test file is
  deleted

#### Scenario: dev-auth remains owned by the sweep

- **WHEN** the sweep needs per-role login
- **THEN** it imports the maintained `e2e/sweep/helpers/dev-auth` implementation
  rather than depending on a deleted harness or an external service

### Requirement: Coverage Catalog and MBT stay out of scope

The `file:line` Coverage Catalog and its drift gate SHALL remain deferred under
`establish-scenario-catalog`, and formal Model-Based Testing SHALL remain
deferred until the catalog and product are ready. Neither MUST be introduced by
this change. This change owns
only the behavior-anchored path and the Driver.

#### Scenario: No file:line coupling and no MBT model is added

- **WHEN** this change is implemented
- **THEN** no scenario, catalog entry, or sweep it adds binds to a `file:line`
  location, and no formal state model is authored; both stay deferred

### Requirement: Negative-authz matrix stays out of scope

A per-role catalog SHALL list only the routes that role can reach, and SHALL NOT
enumerate a negative-authz / denial matrix ("role X is denied route Y"). The
access boundary is a backend concern (the tRPC role-coverage gate + SSR layout
guards); the catalog MUST NOT duplicate it. The Driver MAY report an _unexpected_
denial on a reachable route as an anomaly, but no denial grid is built.

#### Scenario: Catalog carries no denial grid

- **WHEN** a role's catalog is generated
- **THEN** it contains only that role's reachable routes and no "denied" entries,
  and the access boundary is left to the backend gate; an unexpected Forbidden on
  a reachable route surfaces through the Driver's anomaly report, not a catalog
  authz matrix

### Requirement: Per-role sweep produces a blocking accessibility verdict

The Driver SHALL run per role (`lead`, `head`, `admin`, `viewer`) via
`/auth/dev-login` and report anomalies per role: console errors (favicon 404
ignored), broken DOM/flow against the expected outcome, layout issues, and the
result of an `@axe-core/playwright` audit. The sweep MUST write and attach every
role report before applying its verdict. Any reported anomaly MUST fail that
role's test; an axe violation MUST therefore block completion.

#### Scenario: Report names the anomaly with its context

- **WHEN** a role sweep finds a console `error`, a broken flow, or an axe
  violation
- **THEN** the report names the role, route, rule, and offending target
- **AND** the role test fails after the report is written

#### Scenario: Within-route exhaustiveness is the Driver's run-time job

- **WHEN** the Driver runs a role's scenario on a route
- **THEN** it enumerates that route's interactive elements and reachable
  transitions at run time
- **AND** reports per element, so coverage stays measured rather than frozen in
  the catalog

#### Scenario: A boot/load failure is surfaced loudly

- **WHEN** a route fails to load or the app fails to boot
- **THEN** the sweep records the failed route and console evidence
- **AND** the role test fails after preserving the report

#### Scenario: Blocking verdict supersedes phase-1 reporting

- **WHEN** this accessibility closeout supersedes the former phase-1
  report-only behavior
- **THEN** console, load, network, page, and axe anomalies block the UAT command
- **AND** the deferred exhaustive frozen behavior suite remains a separate
  future concern

#### Scenario: A clean role passes

- **WHEN** every catalog route for a role loads with no console, network, load,
  page, or axe anomaly
- **THEN** its report records zero anomalies
- **AND** the role test passes
