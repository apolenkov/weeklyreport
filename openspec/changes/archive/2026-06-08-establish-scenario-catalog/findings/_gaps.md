## 1. Coverage gaps — writer exists in code, no dedicated scenario

These three entities ARE written by production code, but only transitively
inside the section-save transaction. No catalog scenario names them as an
entry point or asserts on their rows. They are written and read as a bundle
("items/risks/decisions") with no per-entity verification.

### 1.1 `Risk` — no dedicated writer OR reader scenario

- **Writer in code:** `report-sections.prisma-repository.ts` and
  `lead-form.prisma-repository.ts` — `tx.risk.deleteMany` + `tx.risk.createMany`
  inside the section saveDraft/submit transaction (delete-and-recreate).
- **Reader in code:** read as part of the section read model; surfaced in
  analytics only as `riskCount` / `riskDelta` aggregates.
- **Catalog state:** `Risk` appears ONLY in compound phrases —
  `items/risks/decisions` (lead-form.feature:102), `riskCount`
  (lead-form.feature:146,383), `riskDelta` (analytics-read.feature:136-140).
  No scenario asserts a Risk row is written with its fields, nor reads a Risk
  back as the unit under test.
- **Gap:** Risk-as-entity has neither a writer nor a reader entry-point
  scenario. Frame: written transitively via section-save, no dedicated assertion.

### 1.2 `StageStatus` — no scenario at all (zero catalog mentions)

- **Writer in code:** `report-sections.prisma-repository.ts` /
  `lead-form.prisma-repository.ts` — `tx.stageStatus.deleteMany` +
  `tx.stageStatus.createMany` in the section-save transaction.
- **Reader in code:** read into the section read model (`row.stageStatuses`),

- **Catalog state:** ZERO occurrences of `StageStatus` / `stage status` /

- **Gap:** the traffic-light scenario (reports-period.feature:121 "saveDraft
  updates the project traffic light") exercises the StageStatus write path
  transitively but never asserts on StageStatus rows. No writer or reader
  entry-point scenario for StageStatus.

### 1.3 `ProjectStatus` — write covered only transitively via traffic light

  (`tx.projectStatus.deleteMany` + `createMany`) and `auth.routes.ts`

## 3. Spec-drift findings — spec claims behavior the code does NOT implement

The `period-dual-state` spec lists six writers of the `Report` period. TWO of
the six do not write any `Report` period field. The spec is wrong, the code is
correct.

### 3.1 CONFIRMED — carry-over is NOT a Report-period writer

- **Spec claim:** period-dual-state/spec.md:27-30 — "Carry-over writer updates
  both fields ... the carry-over path creates or copies a Report into a new
  period ... consistent periodState value and matching legacy tuple."
- **Code reality:** `carry-over.prisma-repository.ts::saveCarryOver` writes
  ONLY child rows in its `$transaction`: `carryOverExecution.create`,
  `carryOverRecord.createMany`, `item.createMany`, `decision.createMany`. It
  never calls `report.update` / `report.create`. Grep for
  `report.(update|create)` in `modules/carry-over` returns nothing;
  `codegraph_callees(saveCarryOver)` returns only types
  (CarryOverExecution, CarryOverRecord, ReportSectionReadModel, CarryOverResult)
  — no Prisma Report writer on the reachable path.
- **Verdict:** SPEC IS WRONG, not the code. Carry-over relies on the target
  Report already carrying both representations (set by period-creator at
  creation). Cataloged as carry-over.feature:131-139.

### 3.2 NEW — lead-section save is NOT a Report-period writer

- **Spec claim:** period-dual-state/spec.md:13-16 — "Lead section save updates
  both fields ... the lead save path in apps/api/src/modules/weekly-report/
  writes a Report ... both periodState and the legacy tuple are updated
  atomically." Also listed at spec.md:25 among "the six known writer paths".
- **Code reality (codegraph-confirmed):** `codegraph_trace(saveDraft →
buildTransition)` returns NO path. `saveDraft`'s full callee set is
  `getActiveSection`, `assertCanEditSection`, `getReportStatus` (read),
  `repository.saveSection`, `mergeSection` — it reaches no `report.update` and
  no period transition. Conversely, `buildTransition`'s callers are EXACTLY
  `createPeriodManual`, `archivePeriod`, `unarchivePeriod`, the auto-archiver
  scheduler, and the period-creator scheduler — the lead-save path is not among
  them, so there is no `scheduled→open` transition fired by first lead save. The
  `weekly-report` module itself has ZERO Prisma mutations; the actual lead-save
  writes land in `report-sections.prisma-repository.ts::saveSection`, whose
  `$transaction` writes only `reportSection`, `item`, `risk`, `decision`,
  `projectStatus`, `stageStatus` — never `report`.
- **Verdict:** SPEC IS WRONG on two counts: (a) it mis-locates the writer — the
  `weekly-report` module performs no Report write at all; and (b) the lead-save
  flow reaches no Report-period write on any path. Same drift class as 3.1 — the
  spec over-counts its six-writer list. The real Report-period writers
  (confirmed): **publication / head-publish** (publication.prisma-repository.ts:56
  spreads `...lifecycle` from `buildTransition`/`publishLifecycle` = periodState
  - legacy tuple in one `report.update` — content inspected); **archive,
    manual admin edit, unarchive** (`archivePeriod` / `createPeriodManual` /
    `unarchivePeriod` in admin.prisma-repository.ts call `buildTransition`, which
    returns periodState + legacy tuple together); the **auto-archiver and
    period-creator schedulers**; and **snapshot-restore** (admin.prisma-repository.ts
    `report.update`, the recognised non-transition writer with its gate opt-out).
    `period-transition.ts::buildTransition` is the canonical field-set source.

## 4. Dead enum states — value never written by any production path

### 4.1 `CarryOverStatus.failed` — DEAD (confirmed)

- Enum: `pending | completed | failed`. Production carry-over code sets status
  to `"completed"` only (carry-over.service.ts:69,99,204). The repository's
  `saveCarryOver` persists `execution.status` (always `"completed"`); no path
  ever writes `"failed"` or `"pending"`. No test asserts `failed`.
- **Dead value.** Cataloged as a gap in carry-over.feature:113-120.

### 4.2 `ReminderRuleStatus.paused` — DEAD as a WRITE (reader exists, no writer)

- Enum: `active | paused`. `ReminderRule.status` defaults to `active`. The
  `reminderRule.create` / `reminderRule.update` calls in
  `admin.prisma-repository.ts` never pass an explicit `status` — no production
  path transitions a rule to `paused`.
- A READER exists: review-reminders.feature:209-212 — the scheduler rejects a
  rule with `status="paused"` (covered by `reminders.contract.test.ts`). The
  schema even carries an anticipatory index `@@index([status, fireAt])`.
- **Verdict:** `paused` is reachable only by manual DB / seed insertion. The
  pause TRANSITION was designed (reader + index) but never implemented — no
  writer entry-point exists. Dead on the write axis.

Run `rg -n "covered: none" e2e/catalog/*.feature` for the full list. These are
the highest-value automation targets: behavior is identified and described,
only the executable test is missing.

NOTE on entry-point parity: `_entry-points.md` counts 99 code-derived entry
points (86 tRPC + 4 REST + 3 BullMQ + 4 cron + 2 Next). The SC-6 drift gate
should re-derive this surface and fail if any entry point has NO catalog
scenario (worse than `covered: none` — uncataloged entirely). That re-derivation
is the gate's job; this gap list flags the `covered: none` subset that IS
cataloged.
