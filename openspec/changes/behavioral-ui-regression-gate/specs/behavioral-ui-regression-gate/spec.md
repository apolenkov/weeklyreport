## ADDED Requirements

### Requirement: Durable behavior-anchored Scenario Catalog

UI behavior SHALL be defined in a durable, high-level **Scenario Catalog** of
Behavioral Scenarios (`role + route + intent + Given/When/Then` expected
outcome), anchored to observable behavior, never to a code location
(`file:line`). The catalog SHALL be stored as a YAML skeleton (`role · route ·
intent`) with the expected outcome as Given/When/Then prose, read and edited by
both humans and the Driver. It SHALL NOT exhaustively enumerate every element,
state, or transition.

#### Scenario: Scenario anchored to behavior, not code

- **WHEN** a Behavioral Scenario is authored for a role/route
- **THEN** it describes only observable behavior (visible DOM, role/aria, console
  state) and contains no `file:line` reference, so it survives a refactor that
  moves the implementing code

#### Scenario: Catalog stays high-level, not exhaustive

- **WHEN** the catalog is reviewed
- **THEN** each entry is a `role × route × intent` scenario, and the catalog does
  NOT contain a frozen per-element/per-transition enumeration — that coverage is
  produced by the Driver at run time

### Requirement: Catalog generated from code+DOM, human-reviewed

The catalog SHALL be generated by a Haiku fan-out over the code+DOM entry-point
surface (one agent per entry-point slice; large files sub-sliced by line-group),
followed by a completeness-critic pass and a coverage matrix, then reviewed by a
human. It MUST NOT be hand-authored scenario-by-scenario, and MUST NOT bind any
scenario to `file:line`.

#### Scenario: Generation derives scenarios from entry points

- **WHEN** the generator runs
- **THEN** it discovers the entry-point surface itself (no hardcoded routes or
  line numbers) and emits one set of Behavioral Scenarios per slice

#### Scenario: Entry-point coverage is justified, not asserted

- **WHEN** generation completes
- **THEN** a completeness-critic pass and a coverage matrix verify **entry-point
  coverage** — that every `role × route` entry point has at least one intent
  scenario — and surface any role/route with no scenario for human review. This
  is coverage of entry points, NOT a per-element/per-transition enumeration; the
  latter is produced by the Driver at run time (see the per-role sweep)

### Requirement: Swappable Driver (human or AI agent)

The Scenario Catalog SHALL be executable by a swappable **Driver**: either a
human (manual checklist) or an AI agent driving the browser via the Playwright
MCP through `/auth/dev-login`. Both read the same catalog. The agent Driver SHALL
be built on the repo's own tooling (Workflow + Playwright MCP), not an external
agentic-testing product.

#### Scenario: The same catalog runs under either driver

- **WHEN** a role's scenarios are executed
- **THEN** a human Driver can walk them as a checklist and an AI-agent Driver can
  drive them in a live browser, both from the same catalog, with no per-driver
  fork of the scenarios

#### Scenario: Agent driver uses owned tooling

- **WHEN** the AI-agent Driver runs
- **THEN** it drives the browser via the Playwright MCP and logs in via
  `dev-auth`, with no dependency on an external testing service

### Requirement: Per-role sweep produces a non-blocking report

The Driver SHALL run per role (`lead`, `head`, `admin`, `viewer`) via
`/auth/dev-login` and report anomalies per role: console errors (favicon 404
ignored), broken DOM/flow against the expected outcome, layout issues, and the
result of an `@axe-core/playwright` audit. In phase 1 the sweep SHALL report
only and MUST NOT block merges.

#### Scenario: Report names the anomaly with its context

- **WHEN** a role sweep finds a console `error`, a broken flow, or an axe
  violation
- **THEN** the report names the role, the route, and the anomaly, without failing
  CI

#### Scenario: Within-route exhaustiveness is the Driver's run-time job

- **WHEN** the Driver runs a role's scenario on a route
- **THEN** it enumerates that route's interactive elements (and reachable
  transitions) at run time and reports per element, so "cover everything" is
  measured and bounded in the run, not frozen as a per-element list in the catalog

#### Scenario: A boot/load failure is surfaced loudly

- **WHEN** a route fails to load or the app fails to boot (the origin-class bug)
- **THEN** the sweep reports that role/route as broken (failed load plus console
  errors), so a human reading the report can catch it

#### Scenario: Phase 1 does not block merges

- **WHEN** the phase-1 sweep finds anomalies
- **THEN** it produces a report and the merge is not blocked by it; a blocking
  verdict is deferred to the phase-2 frozen gate

### Requirement: Deterministic frozen gate deferred to phase 2

Freezing scenarios into deterministic Playwright specs as a blocking gate SHALL
be deferred until the product stabilizes, and SHALL then cover only critical,
stabilized paths — never an exhaustive freeze. This change MUST NOT introduce a
blocking compiled gate.

#### Scenario: No blocking compiled gate is added now

- **WHEN** this change is implemented
- **THEN** no compiled Playwright spec is wired as a merge-blocking gate, and the
  freeze step is recorded as deferred to phase 2

### Requirement: Test-harness boundary

This change SHALL remove the current UI e2e harness under `e2e/` (browser sweep
config, fixtures, `dev-auth`, page helpers, visual helpers, and the
`test:e2e`/`test:e2e:ui` scripts) to be regenerated for the sweep. It MUST keep
the integration suite (`e2e/integration/*`, `playwright.integration.config.ts`)
and all vitest unit tests. The removed `dev-auth` plumbing SHALL be recovered
from git history, not rewritten.

#### Scenario: Integration and unit tests are preserved

- **WHEN** the UI e2e harness is removed
- **THEN** `pnpm test` (vitest unit) and the integration config still run, and no
  unit or integration test file is deleted

#### Scenario: dev-auth is restored from history

- **WHEN** the regenerated sweep needs per-role login
- **THEN** `dev-auth` is restored from git history rather than re-derived from
  scratch

### Requirement: Coverage Catalog and MBT stay out of scope

The `file:line` Coverage Catalog and its drift gate SHALL remain deferred under
`establish-scenario-catalog`, and formal Model-Based Testing SHALL remain
deferred to phase 2. Neither MUST be introduced by this change. This change owns
only the behavior-anchored path and the Driver.

#### Scenario: No file:line coupling and no MBT model is added

- **WHEN** this change is implemented
- **THEN** no scenario, catalog entry, or sweep it adds binds to a `file:line`
  location, and no formal state model is authored; both stay deferred
