## C1 — Review & acknowledgement **(LOCKED)**

### Raw feedback (reconstructed from STT)

- Each group needs reviewers who can review any position; a comment for the review.
- "Another role — reviewer, or a viewer who can review / give feedback"; the head
  can also review. Head ≈ viewer except the head has a dashboard + can lock the
  report; a viewer just observes and (if allowed) reviews for the group.
- A reviewer writes "acknowledged / review passed", or flags where something is
  wrong — like the head can, but **without locking the period**: send feedback now.
- Information must not duplicate; lay out so reviews don't overlap yet all show.
- A viewer "Acknowledged" button — so we know whether a person has seen the report.
- The verdict can un-submit a section ("отправить засабмиченный отчёт обратно"); the
  comment must point at a concrete record so the lead sees exactly what's wrong.
  A future AI review agent will place those per-record comments automatically.
- Default view for head and viewer should show only submitted content; a toggle
  switches to all (incl. drafts), like the lead's "Mine / Everyone" card toggle.

### Locked model

**Reviewing is a capability, not a new enum role.** A new `reviewer` enum value
would detonate `role-coverage-gate` (9 reference-matched builders), the `Role`
migration, and default-role plumbing — and, decisively, `Role` is single-valued
per user, so a `reviewer` role could not coexist with "head can also review".
Review is a capability carried by existing role × group access, riding the
existing `leadershipProcedure` (head + admin + viewer; lead excluded) + group scope.

Capability matrix (all on `leadershipProcedure` + group-scope + a `canReview` check):

```
                   ACK ("Ознакомлен")  VERDICT+COMMENT   UN-SUBMIT section   LOCK period
                   group-level         per-record         (changes_req⇒auto)  (publish)
lead                    —                  —                   —                  —
viewer (plain)          ✓                  —                   —                  —
viewer canReview=✓      ✓                  ✓                   ✓                  —
head (own group)        ✓                  ✓                   ✓                  ✓
admin (all)             ✓                  ✓                   ✓                  ✓
```

Flows:

1. A reviewer opens the group's report live (drafts included — ADR 0007 holds).
2. Comments anchor to **concrete records** (Item / Risk / Decision). Flat, no reply
   threads in MVP. Forward-compatible with a future AI reviewer author.
3. Verdict is **per-section (per lead)**: `approved` (stays submitted) or
   `changes_requested`.
4. `changes_requested` **auto-un-submits** the section (`submitted → draft`) and
   returns it to the lead. Soft feedback = `approved` + comments (no un-submit).
5. Lead sees, **in-app**, the section back in draft + the per-record comments; fixes
   and re-submits.
6. **Acknowledgement** is a separate light group-level signal ("I have seen the
   group's report"); the head can see who acknowledged.
7. **Submitted-visibility toggle** (head + viewer): default shows only submitted
   sections on the **live current period**; toggle reveals all (incl. drafts).
   Published snapshot is shown as-is (not filtered).
8. Only the **head** locks the period (Publish & Lock); review never touches period
   lifecycle.

### Decisions & their consequences

- **ADR 0007 reframed additively** — viewer stays read-only for report _content_;
  review/ack is an orthogonal write surface that does not mutate report rows. The
  submitted-only default _amends_ ADR 0007's v1 "show drafts, don't overcomplicate"
  call — knowingly reversed now, but scoped to the **live current period only** so
  the `publishedSnapshot` reconciliation + `reopened` stickiness the ADR rejected
  stay closed. See ADR 0010.
- **ADR 0008 amended** — un-submit/revoke was head-only; it now extends to
  designated reviewers (incl. viewers with `canReview`). Concurrency: the un-submit
  path must re-check section state inside a transaction (the `ReportSection.version`
  optimistic lock already exists). See ADR 0009.
- **Designation** — verdict/un-submit needs `ViewerGroupAccess.canReview = true`;
  head/admin are reviewers implicitly. Ack needs only access. Tightening the
  reviewer set further can be layered later without remodelling the review acts.

### MVP edge defaults (documented, overridable)

- Delivery: **in-app only**. Telegram / email — Out-of-scope.
- A per-record comment cascade-deletes with its record; it persists on edit.
- No formal "resolved" workflow — a re-submit is implicitly a new review round.
- Multiple reviewers: any `changes_requested` un-submits; verdicts are per-reviewer.
- `changes_requested` on a draft section = comments only (nothing to un-submit).
- "No duplication" → comments render inline at the record, carry the reviewer's
  name, never repeat the record content.

### Out-of-scope for C1

AI review agent (model only leaves room for it) · comment reply-threads ·
Telegram/email notifications · a separate per-record verdict (verdict stays
per-section) · restricting the reviewer set beyond `canReview` · filtering the
published snapshot by submission state.

## C2 — Unified quick entry + carry-over _(stub)_

Leads find entry tedious; they want one fast "quick add" and items that don't get
lost across periods.

- A single quick-entry affordance that picks the record type (item / current /
  next / decision / risk / block) and captures the minimum, fast.
- Possibly fold current-week / next-week into one section split by state
  (done / planned-next / deferred / failed).
- Items carry over so nothing is lost (copy-forward on opening the next period;
  move to complete or to next week).
- Keep the current format too — make the new mode opt-in, perhaps via settings.
- Future: an AI step that turns free text into the right record/action.

Existing footing: `Item.type` (`current|next`), `Item.workflowStatus`
(`done|in_progress|blocked`), `Item.carriedOver`, and a working carry-over service
(`apps/api/src/modules/carry-over/`) that already clones next-week items to current
in the next period. Caution: touches `period-dual-state` and the lead form — high
blast radius. Grill before building.

## C3 — Project activity (non-SDLC reporting unit) _(stub)_

A new weekly reporting unit beside Products: a "project activity" that is like a
product but **without an SDLC stage**, optionally linked to a product, optionally
tied to one or more Jira accounts (Jira not used yet — just a field), reported
weekly with a status (risk / block). Scoped to a group; a lead reports on the
activities they are attached to.

Existing footing: `Project` (Product) + `GroupProduct` (one-group-per-product);
no free-standing activity, no Jira fields anywhere today (confirmed). Largely
additive (new model + section element), lower risk than C2/C1.

## C4 — Slide priority ordering _(stub — root cause found)_

"Priorities look weird on the slide; they should be ordered." Root cause:
`apps/web/src/components/slides/section-slide-utils.ts:188` (and :261, :292) sort
priorities by `(a.priorityRank ?? 0) - (b.priorityRank ?? 0)` — the `?? 0` fallback
sorts **unranked items before P1**. Near-trivial fix: sort nulls last (rank-bearing
items ascending, unranked after). Also note items/risks/decisions otherwise render
in DB insertion order. Small enough that it needs a fix + test, not a grill.

## C5 — Mobile / compact layout _(stub — cross-cutting)_

"Make it more compact" and "think about mobile now — account for it in the layout."
Not a feature; a cross-cutting constraint on every surface above (especially the
C1 review surface: per-record comments stacked without duplication must be
responsive). Capture as a standing constraint + a density/responsive pass.
