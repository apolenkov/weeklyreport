## 1. Отгружено в `main` (3 фикса)

### 1.1 Два диалога при переключении слайд↔редактирование — FIX

Коммит `55938710`.

- **Симптом:** Add Risk → Cancel → режим слайдов → Add Decision → Cancel →
  режим слайдов → всплывают сразу ДВА create-диалога стопкой.
- **Корень:** `ViewModeToggle` — это `<Link>` на тот же маршрут с `?mode=slides`.
  `LeadForm` не перемонтируется, но тело формы рендерится условно, поэтому
  секции Risks/Decisions размонтируются в слайдах и монтируются заново при
  возврате. Хук `useEditableListDialog` инициализировал `lastHandledSignal`
  нулём на каждом маунте, а проп `addSignal` из родителя оставался stale (=1) →
  эффект на маунте читал «сигнал продвинулся» → повторно открывал диалог.
- **Фикс:** `use-editable-list-dialog.ts` — `useRef(addSignal)` вместо
  `useRef(NO_SIGNAL_HANDLED)`. Перемонтирование захватывает stale-значение и
  короткозамыкает эффект; реальный следующий «+ Add» (инкремент) всё ещё
  открывает. Покрывает все 4 секции одной строкой.
- **Тесты:** добавлен D16-регресс (unmount→remount со stale-сигналом остаётся
  закрытым); 4 тест-файла приведены к реальному паттерну (счётчик стартует с 0,
  затем инкремент) — раньше они монтировались сразу с `addSignal=1`, чего в
  жизни не бывает.
- **Проверка:** `pnpm exec vitest run` по хуку + 3 секциям — зелено; pre-push
  прогнал 1305 тестов.

### 1.2 Лид не видит Edit/Delete на СВОИХ decisions — FIX (seed)

Коммит `8855c96`.

- **Симптом (фидбэк «а как редактировать? куда удалить?»):** на редактируемом
  отчёте у лида нет иконок edit/delete на его собственных decisions.
- **Корень:** seed писал `Decision.owner = lead.label` («Василий И.»), а сессия
  несёт полное `User.name` («Иванов Василий Петрович»). `isMine(owner, name)`
  возвращал false → кнопки скрыты, показывался только бейдж «Owner: …». Комментарий
  в seed утверждал, что label уже совпадает с name — это было неправдой.
- **Фикс:** добавлено поле `name` (полное имя) на каждого лида; `owner` сидируется
  из него (основные секции + W6 cross-author секции Boris/Victor/Galina). `label`
  остался для коротких чипов в демо-текстах.
- **⚠ Требуется reseed**, чтобы увидеть вживую — правка только в коде seed
  (`prisma/seed-simple.ts`), существующая БД ещё несёт старые owner-строки. НЕ
  делал reseed автономно: приложение было открыто на текущей БД. Команда —
  именно та, что прогоняет `seed-simple.ts`:
  `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION=1 pnpm db:fresh:simple`
  (`db:reset:hard` + `tsx prisma/seed-simple.ts`). НЕ `db:fresh:manual-uat` —
  он запускает `wipe-manual-uat.ts` (только очистка, без сидирования
  seed-simple), и фикс не применится. Без hard-reset можно `pnpm db:seed:middle`
  (тот же `seed-simple.ts`), если decisions нужно пересоздать поверх.
- **Проверка после reseed:** залогиниться лидом (Иванов Василий Петрович),
  открыть активный отчёт → у своих decisions должны появиться edit/delete.

### 1.3 Обрезается верхняя обводка карточек Portfolio Overview при hover — FIX

## 3. Предложения — НЕ реализовано (нужны проектные решения)

Эти три пункта пользователь сам пометил как «надо доработать / переработать».
Радиус большой, есть развилки дизайна — реализовывать ночью вслепую рискованно.
Ниже — находки и рекомендованное направление; готово под `/openspec-propose`.

### 3.1 Portfolio Overview должен следовать за scope (product ↔ lead)

Страница `/head/report/...?scope=lead`. Также «для вьюера применится автоматически».

- **Текущее состояние:** при `scope=lead` ТЕЛО отчёта уже группируется по лидам
  (`weekly-report-page.tsx:153`, `leadGroups`), НО Portfolio Overview всегда по
  продуктам (`portfolio` проп, стр. 570), и клик скроллит к продукт-аккордеону
  (`report-product-<id>`).
- **Запрос:** в lead-scope overview должен быть ПО ЛИДАМ, и клик по карточке —
  переход к группе лида, а не к продукту.
- **Развилка дизайна (нужно решение):** что показывает карточка лида —
  имя лида + агрегат статуса по всем его продуктам (worst-of?) + суммарные
  счётчики current/next/risks? Куда скроллит клик — к `<section aria-label=group>`?
- **Затрагивает:** `portfolio-overview-table.tsx` (scope-aware вход + якоря),
  `weekly-report-page.tsx` (передать lead-агрегаты), вьюер (тот же overview).
- **Рекомендация:** один проп `scope` + два режима данных; для lead-карточки
  агрегировать статус как «худший из продуктов лида», клик → якорь группы лида.

### 3.2 Этап SDLC без назначенца → исключать из отчётности

Страница `/admin?tab=products` (`products-tab.tsx`).

- **Запрос:** если на этап продукта никто не назначен — этап считается
  неподотчётным и пропускается автоматически (как будто его нет), а не
  показывается серым «unassigned». Так можно исключить лишние этапы (напр. DevOps),
  за которые некому отчитываться.
- **Текущее состояние:** неназначенные этапы показываются как gray/`unassigned`
  (`sdlc-hidden-stages.ts` строит «+N more» reveal именно для таких). То есть
  сейчас они присутствуют, просто помечены пустыми.
- **Развилка дизайна (нужно решение):** «исключён» = скрыт только в UI или
  убран из агрегатов здоровья продукта и из требований к отчёту? Что с этапом,
  у которого сняли назначенца в середине периода (исторические данные)?
  Различать «нет назначенца никогда» vs «временно пусто»?
- **Затрагивает:** SDLC-pipeline рендер, stage-tags, возможно агрегаты
  дашборда/слайдов и валидацию полноты отчёта.
- **Рекомендация:** правило «0 назначенцев на (этап × продукт) ⇒ этап вне
  отчётности этого продукта» провести через OpenSpec — это смена контракта
  отчётности, не косметика.

### 3.3 Заголовок «Telegram» в интеграциях → «элемент» (?)

### 3.4 «Покрыть всё debug-логами» — осознанно отложено

Запрос был: «покрой всё максимально логами… чтобы понять, где места проблемные».

- Это был **способ** найти баг, а не самоцель — а баг (два диалога, п. 1.1)
  уже найден и устранён через разбор кода.
- Широкая спекулятивная инструментация противоречит правилу «хирургических

  `useEditableListDialog` (open/close/addSignal) по отдельному запросу.

## Проверка фикса 1.2 без reseed (linchpin подтверждён)

`isMine` сравнивает `Decision.owner` с `currentUser.name`. Цепочка источника
имени подтверждена по коду — это полное `User.name`, то же, что пишет рантайм:

- `currentUser.name` ← `active.authorName` (`mappers/lead-form.ts:650`)
- `active.authorName` ← `row.user.name` (`lead-form.prisma-repository.ts:444`)
- рантайм-owner при создании = `section.authorName` = `User.name`
  (`report-sections.service.ts:109`)

Значит seed `owner = User.name` совпадёт с `currentUser.name` точно → edit/delete
появятся. Reseed нужен лишь чтобы старые строки в БД сменились на новые.
