## Killed by verification

- **Sub-claim within the StatusBadge duplication finding: 'A third variant (STATUS_BADGE map) exists in product-accordion.tsx' as a third re-styling of the same status vocabulary.**
  Reason: Misread: product-accordion.tsx STATUS_BADGE (lines 131-151) maps the per-ITEM status vocabulary (planned/in-progress/completed/blocked with in-progress/success tokens), not the product tone vocabulary (red/yellow/green/null -> Blocked/At risk/On track/No status). Different domain, different tokens, different labels — not a duplicate of the slide tone mapping. The core two-file duplication finding stands and was kept.

- **Duplication: two useEffects both call identical qc.removeQueries for crossAuthorContent (lead-slides-client.tsx 216-229)**
  Reason: Refuted. The two effects have deliberately different guard semantics: the first purge is skipped while isEveryone && visibilityHydrated; the identity-change purge is unconditional. Merging into one effect with a combined dependency list would SKIP the security purge on an identity change where both users view their own deck (isEveryone stays true) — a regression on the very path the identity guard protects. The shared body is a single 3-line query-client API call with two distinct documented rationales; extracting a named wrapper is cosmetic indirection, not a duplication fix. Not a real smell.

- **Naming/keys: row key `${row.text}-${String(idx)}` mixes array index into the key (lead-unified-slide.tsx 86-88)**
  Reason: Refuted against the calibrated rule. The taste profile prohibits index keys for REORDERABLE lists; these quadrant rows are rebuilt wholesale from UnifiedSlideModel on every data change and are never reordered/inserted in place, and the key also includes row.text. The finding itself concedes it is not a live bug ('not a live reorder bug today') — it is speculative future-proofing. Threading a stableId through buildUnifiedSlideModel for a hypothetical future feature is scope creep, not a current violation.
