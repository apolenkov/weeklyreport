# WeeklyReport: стенд для тестировщиков

Своё приложение на своём компьютере: Kubernetes, свой вход через Keycloak, почта в Mailpit, PDF.
Собирать образы не нужно.

## Что нужно

- **OrbStack** или **Docker Desktop** с включённым Kubernetes.
- Свободно **6 ГБ ОЗУ** для кластера и **10 ГБ** на диске.
- `kubectl`, `helm`, `openssl`, `envsubst`, `curl`, а также Node 26 и `pnpm` (они нужны для загрузки демо-данных).
- Копия репозитория: `git clone https://forge.example.com/example/weeklyreport.git`.
- Доступ к реестру образов `registry.example.com:5005/example/weeklyreport`. Если нужен вход:
  `REGISTRY_USER=<логин> REGISTRY_PASSWORD=<токен> deploy/tester-kit/start.sh`.
- Свободные порты `8080`, `8081`, `8026`. Если на машине уже работает другой стенд, остановите его.

## Запуск

```bash
cd weeklyreport
deploy/tester-kit/start.sh                 # образы из реестра, тег = коммит вашей копии
deploy/tester-kit/start.sh --tag <sha>     # образы другого коммита main
deploy/tester-kit/start.sh --local         # образы wr/*, собранные на этой машине
```

Первый запуск занимает несколько минут. В конце скрипт печатает адреса и пароли. Он безопасно запускается повторно:
заново поднимает доступ к страницам, если он пропал.

## Адреса и пользователи

| Что      | Адрес                                                       |
| -------- | ----------------------------------------------------------- |
| Стенд    | http://localhost:8080 (кнопка **Sign in**, вход через SAML) |
| Почта    | http://localhost:8026 (Mailpit, все письма стенда)          |
| Keycloak | http://localhost:8081 (`admin`, пароль в `secrets.env`)     |

Пользователи: `lead1@customreport.local` (лид), `head@customreport.local` (руководитель),
`viewer@customreport.local` (наблюдатель), `admin@customreport.local` (администратор).
Пароли печатает `start.sh` и хранит файл `~/.local/state/wr-tester/secrets.env`.

## Сброс и остановка

- `deploy/tester-kit/reset.sh` стирает базу стенда и загружает демо-данные заново (спросит «yes»).
- `deploy/tester-kit/stop.sh` удаляет стенд вместе с данными. Пароли остаются в `~/.local/state/wr-tester`.

## Автопроход интерфейса

`deploy/tester-kit/walk.sh` обходит стенд за четыре роли (лид, руководитель, наблюдатель, администратор)
на ширинах 1280 и 375 пикселей. Он нажимает видимые безопасные элементы, возвращает страницу
в исходный вид и записывает видео (одно на роль и ширину).

В отчёт попадают:

- смена состояния и время отклика каждого нажатия;
- консоль и ошибки сети (от 400);
- axe и геометрия: обрезка, наложение, горизонтальная прокрутка;
- скриншоты: страницы целиком и видимых изменений.

Опасные действия (delete, publish, submit, archive, reopen и подобные) в быстром режиме пропускаются с причиной.
Другие безопасные сценарии открывает переменная `CRAWL_SAFE='Имя кнопки;Другая кнопка'`.

```bash
deploy/tester-kit/walk.sh                  # быстрый режим (--quick): первый уровень, все роли и ширины
deploy/tester-kit/walk.sh --roles lead --widths 375 --max-pages 5
deploy/tester-kit/walk.sh --reset          # после прохода вернуть демо-данные
deploy/tester-kit/walk.sh --full           # полный режим, см. ниже
deploy/tester-kit/walk.sh --full --states draft,published --roles lead,head --widths 1280
```

В отчёте `report.md` и `report.json`, рядом `shots/` и `video/`. Нужны `agent-browser` и `ffmpeg`.
Проход меняет данные стенда, поэтому после него запускайте `reset.sh`.

**Быстрый режим** занимает около пяти минут. Роли идут параллельно и делят общий бюджет запросов: API пускает 200 запросов в минуту
и 5 запросов к `/auth` в минуту с одного адреса, значения заданы в коде. Проход укладывается
в 170 и 5 запросов, поэтому вход наблюдателя и администратора начинается примерно на минуту позже.
Ответ 429 попадает в отчёт как `rate-limited`: такой прогон недостоверен, повторите его.

### Полный режим (`--full`)

Полный проход идёт долго (часы, замер в `docs`-прогоне ниже) и нужен перед релизом или после крупных правок интерфейса.

- **Рекурсия.** Каждая открывшаяся поверхность (диалог, меню, вкладка, раскрывашка) обходится до
  `--max-depth` (по умолчанию 3). Внутри поверхности нажимаются только новые элементы, затем страница возвращается
  в родительское состояние; возврат принимается, только если страница совпала с записанным родителем.
- **Страницы.** Для каждой роли и состояния данных берутся готовые входы: отчёт с его адресом и видами
  (`?mode=slides`, `?archive=1`), список периодов, тренды и каждая вкладка администратора как отдельная страница. Ссылки с этих страниц
  обходятся по одной странице на семейство (идентификаторы записей сворачиваются).
- **Повторы.** Одинаковые элементы (строка таблицы, карточка продукта) обходятся образцовой строкой целиком,
  остальные пропускаются с причиной `representative-row` или `representative-family`.
- **Состояния данных.** `walk.sh --full` по очереди готовит на синтетической базе стенда отчёт в состоянии
  `draft`, `submitted`, `returned`, `published`, `archived`, `closed`, `reopened`
  (`reset.sh --crawl-state <состояние> --manifest <файл>`: сброс по защитному скрипту, затем проверенная выборка из базы).
  В каждом состоянии идёт проход чтения всех ролей и ширин, затем синтетический проход лида и руководителя на 1280:
  `Submit`, `Publish`, `Reopen`, `Approve`, `Request changes` выполняются только на подготовленном отчёте.
  Запись, замеченная в запросах, фиксируется находкой `crawl-baseline-mutated`, страница перезагружается и обходится
  с новой базой; уже пройденные элементы не повторяются.
- **Фильтры и переключатели.** Выпадающие списки, вкладки, радио и переключатели покрываются попарно
  (все пары значений, детерминированно); недостижимые сочетания остаются в отчёте с причиной.
- **Отчёт.** В `report.md` и `report.json`: охват по странице (найдено, нажато, пропущено по причинам, ошибки),
  охват фильтров, матрица «элемент × состояние» (`P` нажат, `S` пропущен, `E` ошибка). Достигнутые границы
  (`depth-limit`, `control-limit`) помечают страницу как `limited`, а не как полную. Неизвестный или неуспешный результат не считается успехом.
- **Сброс.** После прохода, в том числе после сбоя, стенд возвращается к демо-данным (`reset.sh --yes`).
  Пока идёт проход, стенд занят: второй запуск мутаций ждёт снятия блокировки `~/.local/state/wr-tester/mutation.lock`.
  Полный проход проверяет, что стенд работает на `customreport_e2e`, Redis DB 15, Mailpit и с выключенным внешним ассистентом
  (при необходимости обновите стенд: `start.sh --local --tag <тег>`).

## Полный прогон с анализом базы и обработчиков (`full-run.sh`)

Одна команда включает сбор данных, прогоняет обходчик и сводит отчёт:

```bash
deploy/tester-kit/full-run.sh                      # быстрый обход + полный обход состояния returned на 1280
deploy/tester-kit/full-run.sh --states all         # ночной режим: все 7 состояний, 6-7 часов
deploy/tester-kit/full-run.sh --walk-args "--roles lead --max-pages 3"   # пробный короткий прогон
```

Что происходит:

1. Postgres стенда перезапускается с `pg_stat_statements` и `auto_explain` (`log_min_duration=50ms`, JSON, без analyze)
   и журналом всех запросов (`log_statement=all`, файл `pgdata/log/wr-run.log`); у api в pod появляется `NODE_V8_COVERAGE=/cov` (emptyDir).
   Чарт продукта не имеет точки расширения для этого, поэтому включение сделано `ALTER SYSTEM` и `kubectl patch` в самом скрипте
   (идемпотентно; `start.sh` при повторном запуске вернёт чарт к исходному виду). Продукт и схема не меняются.
2. `reset.sh` вызывает хуки `WR_PRE_RESET_HOOK` / `WR_POST_RESET_HOOK`: перед каждой очисткой базы собираются журнал api, счётчики Prometheus,
   покрытие V8 и статистика Postgres, после загрузки демо-данных статистика обнуляется. Так ни один отрезок не теряется, а отрезки не пересекаются.
3. `walk.sh --quick` (все роли, 1280 и 375), пауза 70 с под лимит запросов, затем `walk.sh --full --states returned --widths 1280`.
4. e2e не запускается: `e2e/setup` жёстко привязан к `http://localhost:3000`, `dev.runtimeTarget`, dev-входу и собственному сбросу базы,
   а стенд работает на SAML и порту 8080. Нужен параметр базового URL и вход через SAML.
5. `explain.ts` до финального сброса: `EXPLAIN (ANALYZE, BUFFERS)` самых тяжёлых запросов на данных стенда и пробный индекс в транзакции с откатом.
6. Финальный `reset.sh --yes`, затем `analyze.ts` собирает `report.md` и `report.json`.

**Время (замер 05.10, `full-run.sh` без аргументов):** около 24 минут: включение сбора 1 минута, быстрый обход 5 минут, пауза под лимит 70 секунд, полный обход состояния `returned` на 1280 около 16 минут, финальный сброс и анализ 1 минута. Ночной режим `--states all` в 7 раз длиннее полного обхода одного состояния.

Каталог прогона: `~/.local/state/wr-tester/full-run-<время>/` (`--out` меняет путь): `report.md`, `report.json`, `timings.txt`,
`quick/` и `full/` (отчёты обходчика, скриншоты, видео, консоль и сеть), `segments/` (api-логи, метрики, покрытие, статистика),
`logs/` (web, edge, postgres), `explain.json`.

Как определяется «процедура вызвана»: api пишет строку `trpc request start` с именем процедуры и ролью, счётчики Prometheus дублируют её.
Покрытие V8 даёт только число выполненных функций по файлам роутеров: в сборке нет source maps, поэтому имя процедуры по нему не восстановить.
Экран-источник берётся из исходников web (кто вызывает процедуру).

## Если что-то не работает

| Симптом                       | Что делать                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------- |
| «Kubernetes context is …»     | Включите Kubernetes в OrbStack или Docker Desktop, выберите его контекст.       |
| Образы не скачиваются         | Проверьте доступ к реестру, добавьте логин и токен, либо используйте `--local`. |
| «Port … is busy»              | Освободите порт и запустите `start.sh` снова.                                   |
| Страница не открывается       | Запустите `start.sh` ещё раз.                                                   |
| «Too many requests» при входе | Подождите минуту: запросы к `/auth` ограничены по частоте.                      |
