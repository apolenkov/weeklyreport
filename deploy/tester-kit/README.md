# WeeklyReport: стенд для тестировщиков

Своё приложение на своём компьютере: Kubernetes, свой вход через Keycloak, почта в Mailpit, PDF.
Образы собираются на вашей машине одной командой, реестр образов не нужен.

## Что нужно

- **OrbStack** или **Docker Desktop** с включённым Kubernetes.
- Свободно **6 ГБ ОЗУ** для кластера и **25 ГБ** на диске (с образами и кэшем сборки), доступ в интернет для первой сборки.
- `kubectl`, `helm`, `openssl`, `envsubst`, `curl`, а также Node 26 и `pnpm` (они нужны для загрузки демо-данных).
- Копия репозитория: `git clone https://forge.example.com/example/weeklyreport.git`.
- `docker` (он есть в OrbStack и Docker Desktop).
- Свободные порты `8080`, `8081`, `8026`. Если на машине уже работает другой стенд, остановите его —
  или поднимите второй рядом на других портах и в другом namespace:

  ```bash
  NS=wr-tester-2 STATE_DIR=~/.local/state/wr-tester-2 \
    APP_PORT=9080 KC_PORT=9081 MAIL_PORT=9026 deploy/tester-kit/start.sh
  ```

## Запуск

```bash
cd weeklyreport
deploy/tester-kit/build-images.sh          # соберёт wr/{api,migrate,web,backup}, тег = коммит вашей копии (10–15 минут)
deploy/tester-kit/start.sh                 # поднимет стенд на самых свежих собранных образах
deploy/tester-kit/start.sh --tag <sha>     # образы другого коммита (сначала build-images.sh --tag <sha>)
deploy/tester-kit/start.sh --registry <префикс>   # образы из своего реестра вместо локальных
```

Первый запуск занимает несколько минут. В конце скрипт печатает адреса и пароли. Он безопасно запускается повторно:
заново поднимает доступ к страницам, если он пропал.

## Адреса и пользователи

| Что      | Адрес                                                       |
| -------- | ----------------------------------------------------------- |
| Стенд    | http://localhost:8080 (кнопка **Sign in**, вход через SAML) |
| Почта    | http://localhost:8026 (Mailpit, все письма стенда)          |
| Keycloak | http://localhost:8081 (`admin`, пароль в `secrets.env`)     |

Пользователи: `lead1@weeklyreport.local` (лид), `head@weeklyreport.local` (руководитель),
`viewer@weeklyreport.local` (наблюдатель), `admin@weeklyreport.local` (администратор).
Пароли печатает `start.sh` и сохраняет в файл `~/.local/state/wr-tester/secrets.env`.

## Вход кнопкой роли

На странице входа Keycloak над формой стоят четыре кнопки: **Lead**, **Head**, **Viewer**, **Admin**. Кнопка подставляет
логин и пароль роли в форму и отправляет её, то есть вход идёт обычным SAML, пароль вводить не нужно. Тема
`weeklyreport-test` лежит в `keycloak-theme/`; `setup.sh` подставляет в неё пароли из `secrets.env` и кладёт в Kubernetes
как ConfigMap `keycloak-theme`, так что в Git пароли не попадают. Тема работает только на этом локальном стенде.
Если нужен другой пользователь, введите логин и пароль вручную в форму ниже кнопок.

Частые входы подряд с одного адреса упираются в лимит приложения («rate_limit_exceeded», подождите минуту).

## Сброс и остановка

- `deploy/tester-kit/reset.sh` стирает базу стенда и загружает демо-данные заново (спросит «yes»).
- `deploy/tester-kit/stop.sh` удаляет стенд вместе с данными. Пароли остаются в `~/.local/state/wr-tester`.

## Автопроход интерфейса

`deploy/tester-kit/walk.sh` обходит стенд от имени четырёх ролей (лид, руководитель, наблюдатель, администратор)
на ширинах 1280 и 375 пикселей. Он нажимает видимые безопасные элементы, возвращает страницу
в исходный вид и записывает видео (одно на роль и ширину).

В отчёт попадают:

- смена состояния и время отклика каждого нажатия;
- консоль и ошибки сети (ответы с кодом 400 и выше);
- axe и геометрия: обрезка, наложение, горизонтальная прокрутка;
- скриншоты: страницы целиком и видимых изменений.

Опасные действия (delete, publish, submit, archive, reopen и подобные) в быстром режиме пропускаются с причиной.
Другие безопасные сценарии открывает переменная `CRAWL_SAFE='Имя кнопки;Другая кнопка'`.

```bash
deploy/tester-kit/walk.sh                  # быстрый режим (--quick): первый уровень, все роли и ширины
deploy/tester-kit/walk.sh --roles lead --widths 375 --max-pages 5
deploy/tester-kit/walk.sh --reset          # после прохода вернуть демо-данные
deploy/tester-kit/walk.sh --full           # полный режим, см. ниже
deploy/tester-kit/walk.sh --full --states draft,published --roles lead,head --widths 1280
```

Результат лежит в `report.md` и `report.json`, рядом `shots/` и `video/`. Нужны `agent-browser` и `ffmpeg`.
Проход меняет данные стенда, поэтому после него запускайте `reset.sh`.

**Быстрый режим** занимает около пяти минут. Роли идут параллельно и делят общий бюджет запросов: API пускает 200 запросов в минуту
и 5 запросов к `/auth` в минуту с одного адреса; значения заданы в коде. Проход укладывается
в 170 запросов и 5 запросов к `/auth` в минуту, поэтому вход наблюдателя и администратора начинается примерно на минуту позже.
Ответ 429 попадает в отчёт как `rate-limited`: такой прогон недостоверен, повторите его.

### Полный режим (`--full`)

Полный проход идёт долго и нужен перед релизом или после крупных правок интерфейса. Замеры и сравнение двух прогонов подряд
записываются в карточку задачи TASK-145.55 и в каталог доказательств; `scripts/ui-crawl/compare.ts <прогон-1> <прогон-2>`
сравнивает числа нажатий и пропусков `gone` по роли и ширине (`IDENTICAL` и код 0, когда они совпали).

- **Рекурсия.** Каждая открывшаяся поверхность (диалог, меню, вкладка, раскрывающийся блок) обходится до
  `--max-depth` (по умолчанию 3). Внутри поверхности нажимаются только новые элементы, затем страница возвращается
  в родительское состояние; возврат принимается, только если страница совпала с записанным родителем.
- **Страницы.** Для каждой роли и состояния данных берутся готовые входы: отчёт с его адресом и видами
  (`?mode=slides`, `?archive=1`), список периодов, тренды и каждая вкладка администратора как отдельная страница. Ссылки с этих страниц
  обходятся по одной странице на семейство (идентификаторы записей сворачиваются).
- **Повторы.** Одинаковые элементы (строка таблицы, карточка продукта) обходятся образцовой строкой целиком,
  остальные пропускаются с причиной `representative-row` или `representative-family`.
- **Состояния данных.** `walk.sh --full` по очереди готовит на синтетической базе стенда отчёт в состоянии
  `draft`, `submitted`, `returned`, `published`, `archived`, `closed`, `reopened`
  (`reset.sh --crawl-state <состояние> --manifest <файл>`: сброс по защитному скрипту, затем проверенная выборка из базы).
  В каждом состоянии идёт проход чтения всех ролей и ширин, затем синтетический проход лида и руководителя на 1280.
  Вкладки администратора не зависят от состояния отчёта, поэтому администратор проходит их полностью только в первом
  состоянии запуска; в остальных состояниях идут лид, руководитель и наблюдатель (это самая долгая роль, на ней держалось время прохода):
  `Submit`, `Publish`, `Reopen`, `Approve`, `Request changes` выполняются только на подготовленном отчёте.
  Запись, замеченная в запросах, фиксируется находкой `crawl-baseline-mutated`, страница перезагружается и обходится
  с новой базой; уже пройденные элементы не повторяются.
- **Фильтры и переключатели.** Выпадающие списки, вкладки, радиокнопки и переключатели покрываются попарно
  (все пары значений, детерминированно); недостижимые сочетания остаются в отчёте с причиной.
- **Отчёт.** В `report.md` и `report.json`: охват по странице (найдено, нажато, пропущено по причинам, ошибки),
  охват фильтров, матрица «элемент × состояние» (`P` нажат, `S` пропущен, `E` ошибка). Достигнутые границы
  (`depth-limit`, `control-limit`) помечают страницу как `limited`, а не как полную. Неизвестный или неуспешный результат не считается успехом.
- **Сброс.** После прохода, в том числе после сбоя, стенд возвращается к демо-данным (`reset.sh --yes`).
  Пока идёт проход, стенд занят: второй запуск мутаций ждёт, пока снимется блокировка `~/.local/state/wr-tester/mutation.lock`.
  Полный проход проверяет, что стенд использует базу `weeklyreport_e2e`, Redis DB 15 и Mailpit, а внешний ассистент выключен
  (если нет, пересоберите образы и обновите стенд: `build-images.sh` и `start.sh`).

## Полный прогон с анализом базы и обработчиков (`full-run.sh`)

Одна команда включает сбор данных, прогоняет обходчик и сводит отчёт:

```bash
deploy/tester-kit/full-run.sh                      # быстрый обход + полный обход состояния returned на 1280
deploy/tester-kit/full-run.sh --states all         # все 7 состояний, около 2 часов (оценка: 7 × 16 минут)
deploy/tester-kit/full-run.sh --walk-args "--roles lead --max-pages 3"   # пробный короткий прогон
```

Что происходит:

1. Сбор включён в `values-tester.yaml`, а не в скрипте: `postgres.args` (`pg_stat_statements`, `auto_explain` с `log_min_duration=50ms`,
   JSON, без analyze, журнал всех запросов `log_statement=all` в `pgdata/log/wr-run.log`) и `api.extraEnv.NODE_V8_COVERAGE`
   (каталог `cov` тома pdfdata: том переживает перезапуск контейнера, который сбрасывает покрытие на диск; `full-run.sh` очищает его после сбора).
   Обе точки расширения чарта (`postgres.args`, `api.extraEnv`) по умолчанию пусты и в проде не используются. `start.sh` применяет values;
   `full-run.sh` проверяет, что стенд работает и сбор включён, и иначе сам запускает `start.sh` с образом, который развёрнут сейчас
   (образ этого коммита в реестре может ещё не существовать); если ничего не развёрнуто, `start.sh` берёт образ по умолчанию. Ни `ALTER SYSTEM`, ни `kubectl patch` не остаётся:
   стенд после прогона в том же виде, что задан values. Журнал всех запросов нужен для поиска N+1; значения в нём синтетические.
2. `reset.sh` вызывает хуки `WR_PRE_RESET_HOOK` / `WR_POST_RESET_HOOK`: перед каждой очисткой базы собираются журнал api, счётчики Prometheus,
   покрытие V8 и статистика Postgres, после загрузки демо-данных статистика обнуляется. Так ни один отрезок не теряется, а отрезки не пересекаются.
3. `walk.sh --quick` (все роли, 1280 и 375), пауза 70 с под лимит запросов, затем `walk.sh --full --states returned --widths 1280`.
   Потом синтетический сценарий (п. 4) и `dogfood.sh`: вход четырёх ролей, ключевые страницы (скриншот, снимок, консоль, ошибки страницы) и Jev.
   **Роль Jev.** Jev (`@jkudish/jev-browser`) — это модель действий: она ведёт страницу и возвращает шаги, а не текстовый вердикт. Поэтому Jev не судья
   в смысле «годно / негодно», а второй источник сигналов: нажал (не должен был, это страница чтения), ушёл со страницы, застрял, ошибки запросов в консоли.
   Сигнал — это повод посмотреть скриншот. `PASS` страницы выносится только по снимку страницы и ошибкам браузера (скрипт `dogfood.sh`).
   Исследовательский проход навыка `dogfood` агент дописывает в `dogfood/dogfood-notes.md` вручную поверх этих доказательств; он попадает в раздел отчёта.
   Без `TYPESAFE_API_KEY` `dogfood.sh` сам пропускает Jev (напишет об этом) и выносит `PASS` по снимку и ошибкам.
4. **Синтетический сценарий** (`scripts/ui-crawl/scenario*.ts`, каталог `scenarios/`): на только что сброшенном стенде от имени администратора,
   лида и руководителя вызываются обработчики, которые обходчик пропускает как опасные: создание и удаление записей, жизненный цикл отчёта
   (возврат секции, сохранение, отправка, план, отзыв, публикация, PDF, архив, переоткрытие), напоминания, подсказки и провайдер ИИ (без внешнего вызова).
   Это вызовы `/trpc` из страницы вошедшей роли, а не нажатия; в отчёте колонка `via` говорит, откуда пришёл успешный вызов (`ui`, `scenario`).
   Записи создаёт и удаляет сам сценарий (новые uuid), затем стенд сбрасывается. Шаг, который должен быть отклонён защитой, помечен `refused`.
   Каждая процедура, которую не вызвал ни интерфейс, ни сценарий, получает в отчёте причину из `scripts/full-run/reasons.ts`
   (dev-режим, внешний вызов, нужен упавший job); процедура без причины выводится как `unclassified`.
   e2e (`pnpm test:e2e`) на стенде не запускается (причина в разделе «Почему на стенде нет e2e»); `full-run.sh` пишет об этом в `e2e.txt`.
5. `explain.ts` до финального сброса: `EXPLAIN (ANALYZE, BUFFERS)` самых тяжёлых запросов на данных стенда и пробный индекс в транзакции с откатом.
6. Финальный `reset.sh --yes`, затем `analyze.ts` собирает `report.md` и `report.json`.

**Время (замер 5 октября 2026 года, `full-run.sh` без аргументов):** около 24 минут: включение сбора 1 минута, быстрый обход 5 минут, пауза под лимит 70 секунд, полный обход состояния `returned` на 1280 около 16 минут, финальный сброс и анализ 1 минута. Ночной режим `--states all` в 7 раз длиннее полного обхода одного состояния.

Каталог прогона: `~/.local/state/wr-tester/full-run-<время>/` (`--out` меняет путь): `report.md`, `report.json`, `timings.txt`,
`quick/` и `full/` (отчёты обходчика, скриншоты, видео, консоль и сеть), `segments/` (api-логи, метрики, покрытие, статистика),
`logs/` (web, edge, postgres), `explain.json`.

Как определяется «процедура вызвана»: api пишет строки `trpc request start` (процедура, роль) и `trpc request end` (`status: success` или `error`);
процедура считается проверенной, только если хотя бы один вызов завершился успешно. Отклонённый вход или упавший обработчик — это «вызвана, но не проверена».
Покрытие V8 даёт только число выполненных функций по файлам роутеров: в сборке нет source maps, поэтому имя процедуры по нему не восстановить.
Экран-источник берётся из исходников web (кто вызывает процедуру).

## Почему на стенде нет e2e

e2e (`pnpm test:e2e`) с этим стендом несовместим. Он работает только с приложением, запущенным из исходников (`pnpm dev`) в режиме dev-входа
на базе `weeklyreport_e2e`. Адрес приложения задаёт `E2E_BASE_URL`, но e2e по-прежнему входит через `/auth/dev-login`, вызывает `dev.runtimeTarget`
и сам сбрасывает базу. На стенде вход идёт через SAML, dev-режима нет, поэтому e2e здесь не запустится.

Браузерные проверки на стенде — это `walk.sh` (автопроход) и `full-run.sh` (полный прогон с анализом базы). Шаг `e2e` в `full-run.sh` всегда
пропускается с этим объяснением; флаг `--no-e2e` убирает только саму запись.

## Если что-то не работает

| Симптом                       | Что делать                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------- |
| «Kubernetes context is …»     | Включите Kubernetes в OrbStack или Docker Desktop, выберите его контекст.             |
| «Image wr/… is missing»       | Запустите `build-images.sh` (с тем же `--tag`, что и у `start.sh`).                   |
| Стенд падает на миграции      | Пересоберите образы `build-images.sh`: он сам проверяет движок Prisma в `wr/migrate`. |
| «Port … is busy»              | Освободите порт и запустите `start.sh` снова.                                         |
| Страница не открывается       | Запустите `start.sh` ещё раз.                                                         |
| «Too many requests» при входе | Подождите минуту: запросы к `/auth` ограничены по частоте.                            |

## Нагрузка

`deploy/tester-kit/load/read-pages.js` — k6-сценарий чтения страниц (лид и руководитель, 20 пользователей, 3 минуты):
`LEAD_PW=… HEAD_PW=… k6 run deploy/tester-kit/load/read-pages.js` (пароли PW_LEAD1 и PW_HEAD из `secrets.env`).
